## Problem Statement

현재 파이프라인은 법 조항, 문서유형, 렌더링 형식과 비공개 판정을 너무 강하게
결합한다. 그 결과 세 가지 문제가 생긴다.

1. `T5-5_meeting_pending.pdf`는 회의록 본문을 `official_form.html` 안에 넣어
   수신·발신기관·결재선·시행번호가 있는 내부결재 공문처럼 보인다.
2. 제1~4호는 실제 후보 탐지 경로가 없고 조항 시나리오만으로 C 문서를 생성한다.
   기관, 담당부서, 원문 내용의 중요도를 확인하지 않아 평범한 기관 문서도 기밀처럼
   보일 수 있다.
3. span 근거 생성은 annotated 문서를 읽지만 문서 첫 4,000자만 LLM에 보낸다.
   근거 span은 별도 한 줄로 전달되므로, 근거 주변의 절·표·앞뒤 문단이 잘릴 수 있다.

## What Makes This Cool

목표는 “기밀처럼 보이는 합성 PDF”가 아니라, 실제 공공문서의 형식을 보존하면서
왜 특정 조항 후보인지 추적 가능한 데이터셋이다. 각 결과에서 기관·부서·내용 근거,
선택된 실제 문서형식, 참고 원본과 판정 점수를 되짚을 수 있어야 한다.

## Constraints

- 일반 공공기관도 소송, 수사협조, 시설보안 업무를 수행할 수 있으므로 기관
  화이트리스트만으로 제1~4호를 배제하지 않는다.
- 대통령실·국방부·검찰·법원·경찰 등은 강한 사전확률 신호지만, 내용상 근거 없이
  C 판정을 확정하지 않는다.
- 실제 비밀정보를 생성하거나 세부 작전·수사기법을 보강하지 않는다.
- 현재 tuned keyword 필터와 annotated span, 기관 해석기는 재사용한다.
- 실물 원본 근거가 없는 53개 템플릿 등록은 “형식 검증 완료”로 간주하지 않는다.
- PDF 대량 생성은 원본형식과 판정 게이트가 검증될 때까지 중단한다.

## Premises

1. 법 조항은 비공개 사유이며 문서 레이아웃을 결정하지 않는다.
2. 문서형식은 원본의 구조적 증거로 선택해야 한다.
3. 제1~4호 C 판정에는 기관·부서 적합성과 내용상 근거가 모두 필요하다.
4. 기관·부서는 절대 허용목록이 아니라 점수화된 강한 사전조건이다.
5. LLM에는 더 긴 문서 앞부분이 아니라 근거 span 중심의 구조화된 문맥을 보낸다.
6. 후보 판정과 문서 재구성은 별도 단계여야 한다.

## Approaches Considered

### Approach A: 최소 교정

T5-5 레이아웃, 제1~4호 하한 점수, anchor 중심 문맥만 고친다. 가장 빠르지만
원본 근거가 없는 템플릿을 정상 템플릿으로 취급하는 구조는 남는다.

### Approach B: 증거 우선 전면 재설계

후보 탐지부터 템플릿 승격까지 전체 파이프라인을 한 번에 교체한다. 장기 구조는
좋지만 기존 후보 규칙과 생성 경로를 동시에 바꿔 회귀 원인을 분리하기 어렵다.

### Approach C: 단계적 증거 우선 전환

판정 오류를 먼저 차단하고, 실제 문서와 다른 템플릿을 격리한 뒤, 실물 원본이
확보된 형식부터 승격한다. 기존 저비용 필터와 annotated 문서를 재사용한다.

## Recommended Approach

Approach C를 채택한다. 아래 네 단계는 각각 독립적으로 검증하고 되돌릴 수 있다.

### 1단계: 제1~4호 증거 게이트

후보마다 다음 증거를 구조화해 저장한다.

| 증거 축 | 범위 | 예시 |
|---|---:|---|
| 기관 권한 | 0~3 | 국방·수사·재판·정보·교정 기능과 기관의 관계 |
| 담당부서 적합성 | 0~3 | 법무, 수사, 안보, 비상계획, 시설보안 등 |
| 내용 근거 | 0~6 | 진행 중 절차, 보호 대상, 공개 시 구체적 위해 |
| 문서 구조·상태 | 0~2 | 사건번호, 보안등급, 진행상태, 제한 표기 |
| 반대 증거 | 0~-4 | 이미 공개·종결·보도된 일반 정책자료 |

초기 제안 기준은 총점 8점 이상, 내용 근거 4점 이상, 기관+부서 근거 2점
이상이다. 점수와 별개로 원문의 근거 span을 반드시 보존한다. 기준값은 고정 진리가
아니며 라벨된 평가셋으로 조정한다.

게이트 결과는 `eligible`, `review`, `reject`로 나눈다. `review`는 합성 생성으로
넘기지 않고 사람 검토 큐로 보낸다. 제1~4호에 실제 후보 규칙이 없다는 현재 상태를
먼저 해소하고, 가상 시나리오 폴백으로 C 문서를 만드는 경로는 기본 비활성화한다.

### 2단계: anchor 중심 ContextPack

문서 앞 4,000자 절단을 다음 구조로 교체한다.

```text
ContextPack
├── 원본 메타데이터: 제목, 기관, 담당부서, 문서유형, 생산일자
├── 문서 도입부: 제목과 목적을 이해하는 데 필요한 첫 섹션
├── 근거 anchor: 매칭 span 원문
├── 지역 문맥: 앞뒤 8개 span 또는 앞뒤 각 1,500자
├── 구조 문맥: 가장 가까운 상위 제목, 표 제목과 열 머리글
└── 판정 근거: 매칭 규칙과 증거 점수
```

전체 예산은 우선 10,000~12,000자로 두되 anchor와 상위 제목은 절대 잘리지 않게
한다. 문맥이 겹치면 중복 제거하고 원본 페이지·span ID를 유지한다. LLM은 이
ContextPack을 보고 근거를 판정하며, 판정 통과 후 별도 호출이 문서를 재구성한다.

### 3단계: 문서형식과 조항 분리

렌더링 선택 키를 법 조항 중심의 `T5-5`에서 문서형식 중심으로 바꾼다.

```text
법 조항/세부조항 ──> 비공개 근거와 검증 규칙
문서유형/원본형식 ──> 레이아웃과 섹션 구조
행정상태       ──> 결재·검토·협의 상태 변형
```

`meeting_minutes`의 기본 렌더러는 독립 회의록이어야 한다. 회의명, 일시·장소,
참석자, 안건, 발언 또는 질의응답, 논의·의결 결과를 표시하고, 원본에 없는 수신란,
기관장 발신, 결재선, 시행번호를 붙이지 않는다. 회의 결과를 결재 상신하는 별도
문서만 `approval_memo` 또는 `official_dispatch` 형식을 사용한다.

최소 렌더링 계열은 다음과 같다.

- `standalone_minutes`: 독립 회의록
- `approval_memo`: 내부결재·품의
- `official_dispatch`: 수신처가 있는 시행 공문
- `structured_report`: 조사·점검·기술 보고서
- `plan_draft`: 계획안
- `reply_notice`: 민원·처분 회신
- `tabular_register`: 명부·인사·단가표

### 4단계: 원본형식 레지스트리와 승격 게이트

전용 템플릿마다 다음 provenance를 요구한다.

- 참고 원본 경로와 해시
- 추출한 구조: 상단 필드, 섹션 순서, 표 열, 서명·결재·하단 블록
- 적용 가능한 기관·출처·문서유형
- 실물 원본 수와 형식 신뢰도
- 시각 검수 결과와 검수자

상태는 `provisional`, `source_backed`, `approved`로 관리한다. 현재 53개 목표
조합은 우선 `provisional`로 낮추고 자동 대량 생성 대상에서 제외한다. 서로 다른
실물 원본 2건 이상에서 구조가 확인되고 회귀 테스트와 시각 검수를 통과한 형식만
`approved`로 승격한다.

## Open Questions

- 기관·부서 권한 사전을 수동 관리할지 DB의 기관 계층과 업무명을 학습할지
- 제1~4호별 positive/negative 평가셋을 각각 몇 건 확보할 수 있는지
- 긴 표가 anchor 근거일 때 표 전체를 보낼지 관련 행과 머리글만 보낼지
- 회의록의 발언자 실명을 합성할지 직책·익명 표기로 제한할지
- 동일 문서가 여러 조항 후보일 때 다중 라벨을 허용할지 최우선 근거만 남길지

## Success Criteria

- T5-5 회의록 결과에 수신란, 기관장 발신, 결재선, 시행번호가 없다.
- 제1~4호 negative 평가셋에서 C 자동확정 오탐률이 1% 미만이다.
- 제1~4호 자동확정 결과의 100%가 기관/부서 근거와 내용 span을 함께 가진다.
- 모든 LLM ContextPack에 anchor, 가장 가까운 상위 제목, 앞뒤 문맥이 포함된다.
- 원문 앞 4,000자 밖의 anchor도 잘리지 않고 전달된다.
- 판정 결과에 사용된 page/span ID와 점수 구성요소가 기록된다.
- `approved` 템플릿은 모두 실물 원본 provenance와 구조 회귀 테스트를 가진다.
- 근거 없는 `provisional` 템플릿은 운영 대량 생성 경로에서 선택되지 않는다.

## Distribution Plan

새 외부 배포물은 없다. 기존 생성 파이프라인과 PDF 산출물에 적용한다. CI에서는
증거 게이트 단위 테스트, ContextPack 경계 테스트, 템플릿 구조 스냅샷 테스트를
실행한다. 시각 PDF 검수는 승인 후보 템플릿에 한해 별도 샘플 작업으로 수행한다.

## Dependencies

- annotated JSON의 page/span 순서와 상위 제목 정보
- 기관명 해석기와 DB의 실제 기관·생산일자 메타데이터
- 담당부서가 있는 원본 또는 신뢰 가능한 부서 추출
- 제1~4호 positive/negative 평가 문서
- 실제 독립 회의록과 결재 상신 문서의 원본 샘플

## Next Steps

1. 1~4호 평가셋과 판정 근거 스키마를 먼저 확정한다.
2. prefix 절단을 anchor 중심 ContextPack 빌더로 교체한다.
3. 판정 호출과 재구성 호출을 분리하고 `review` 큐를 만든다.
4. T5-5를 `standalone_minutes`로 교체하는 구조 테스트를 작성한다.
5. 53개 템플릿을 `provisional`로 표시하고 대량 생성에서 제외한다.
6. 실물 원본을 확보한 형식부터 `source_backed`와 `approved`로 승격한다.

## The Assignment

코드를 바꾸기 전에 제1~4호 원본 30건을 고른다. 명백한 양성 10건과 일반 기관의
유사하지만 비기밀인 음성 20건을 포함하고, 각 문서에 기관 적합성, 담당부서 적합성,
내용상 근거 span, 반대 증거, 최종 판정을 기록한다. 동시에 독립 회의록 원본 3건과
회의결과 결재 상신 문서 2건을 확보해 구조 차이를 표로 비교한다.

## What I noticed about how you think

- “회의록이라고 되어있지만 사실 내부결재 문서 형식”이라고 결과물의 의미가 아니라
  외형 구조를 문제 삼았다. 이 구분이 템플릿 품질의 핵심이다.
- “일반 공공기관이 1~4 조항을 넣기만 해도 기밀”이 되는 문제를 기관명만이 아니라
  작성 부서와 내용의 중요도까지 연결했다.
- 단순히 토큰을 늘리자는 말이 아니라 “앞뒤 내용을 더 많이” 보자는 제안은 후보
  anchor의 지역 문맥이 판정 근거라는 방향과 맞는다.
