## Problem Statement

원문 기반 S 문서 생성에서 `지원자의 전화번호 및 이메일 주소`처럼 개인정보
항목을 설명하기만 한 문서가 S로 통과했다. P1은 목표 라벨과 세부조항 이름을
보며 그 표현을 본문에 되풀이했고, P2는 실제 개인과 구체값의 연결이 아니라
본문에 존재하는 인용문만 제출했다. 현재 결정론적 검증은 인용문이 블록에
존재하는지는 확인하지만, 그 인용문이 S를 성립시키는 관계인지 확인하지 않는다.

이번 작업은 원문을 참고해 생성하는 S 데이터에만 적용한다. C 생성과 C의 시각
레이아웃 판정은 범위 밖이다. 최종 RD-1 학습 라벨은 PDF 문서 단위의 S/O
등급이며, span과 관계 정보는 생성 품질을 검증하기 위한 내부 데이터다.

## What Makes This Cool

S를 `전화번호` 같은 낱말이나 정규식 패턴으로 판정하지 않고,
`식별 가능한 사람 → 개인 속성 → 구체적인 값 또는 개인 사정`이라는 관계로
컴파일한다. 같은 원문에서 나온 O/S 문서가 문체와 서식을 공유하도록 만들 수
있어, RD-1이 합성 문체 대신 실제 민감성의 원인을 학습하게 된다.

## Constraints

### 생성 경로와 라벨

- 원문 참고 생성 경로는 S/O만 취급한다.
- C는 별도의 완전 가상 생성 경로에 의존하며 이번 변경에서 다루지 않는다.
- S를 요청했는데 P2가 O로 판정하면 O로 재활용하지 않는다. 한 번 재생성하고,
  다시 O면 해당 건을 제외한다.
- 원문 문맥상 신청인·민원인·지원자 개인정보가 자연스럽게 들어갈 수 없으면
  억지로 S로 바꾸지 않고 건너뛴다.
- 원문 기반 산출물의 파일명은 원문 파일명을 보존한다. 원문 없는 신규 생성은
  생성된 글의 제목을 파일명으로 쓴다는 기존 출력 규칙을 유지한다.

### S/O 판정 정책

- 개인정보의 항목명, 수집 목적, 처리 절차만 설명하면 O다.
- 사람 이름만 있으면 O다.
- 신청인·민원인·지원자 등 외부인의 식별자와 실제 형식의 가상 개인정보가
  명시적으로 연결되면 S다.
- 이름과 건강·복지·신청 사정이 연결된 경우에도 S다.
- 기관 직원의 이름·부서·직위·업무 연락처는 O다.
- 직원의 인사평가·징계내역은 이 연구 라벨 정책에서 O다.
- 직원의 주민·외국인등록번호, 여권·운전면허번호, 개인 연락처·주소,
  계좌·급여, 건강·장애정보는 특정 직원과 연결되면 S다.
- 개인별 행이나 식별자가 없는 집계·통계 정보는 O다.
- 부분 마스킹 또는 간접 식별은 자동 S가 아니라 `hard_case`다.
- 신청번호·사건번호와 민감한 개인 사정만 연결된 경우도 `hard_case`다.
  실명·전화번호 등 직접 식별정보까지 연결되면 S다.
- 자연스러운 형식의 가상 인물과 가상 개인정보를 사용할 수 있다. 본문에
  `가상`, `예시`, `홍길동`, `010-0000-0000` 같은 인공적 표지를 반복하지 않는다.

### 경계 사례와 데이터 분할

- `hard_case`를 임의 비율로 생성하지 않는다. 원문에서 자연스럽게 발생한
  사례만 수집한다.
- `hard_case`는 사람의 S/O 확인 전에는 학습 데이터로 내보내지 않는다.
- 같은 원문에서 생성한 O/S 대응쌍은 동일한 source group ID를 가지며,
  train/validation/test 중 하나의 분할에 함께 배치한다.

### 독립성 및 최종 산출물

- S/O P2는 P1의 목표 라벨, 세부유형, 이유와 evidence를 보지 않는다.
- P2는 생성 IR만 보고 S/O 또는 `hard_case`를 판단한다.
- 최종 모델의 입력은 PDF이므로, S 승인 근거는 렌더링된 PDF에서도 회수되어야
  한다. IR에서만 보이고 PDF에서 사라진 근거는 최종 통과시킬 수 없다.
- 기술적으로 두 LLM 호출이 끝났다는 `succeeded`와 학습 데이터로 승인됐다는
  상태를 분리한다.

## Premises

1. S의 핵심 신호는 개인정보 관련 단어가 아니라 사람과 개인 정보의 연결이다.
2. span은 학습 정답이 아니라 S/O 라벨의 품질을 검증하는 내부 장치다.
3. 명확한 S, O, 사람 검수가 필요한 `hard_case`는 서로 다른 결과 상태다.
4. 목표 S가 O로 판정된 산출물을 O 데이터로 재사용하면 목표 분포와 생성 실패가
   섞이므로 재생성 후 제외해야 한다.
5. 경계 사례는 필요하지만, 애매한 정답 라벨은 허용하지 않는다.
6. PDF 입력 모델을 위한 근거는 최종 PDF에서도 보존되어야 한다.

## Cross-Model Perspective

독립 검토는 이 구조를 “PDF-grounded privacy assertion compiler”로 정리했다.
P2가 `주체–속성–구체값–연결근거`를 제출하고, 코드가 span의 실재와 연결을
검증한 뒤에만 S를 승인하라는 제안이다.

검토는 고유 신청번호만으로 실제 개인에게 재연결할 수 있다고 가정하는 위험도
지적했다. 이에 따라 `신청번호 + 개인 사정`은 `hard_case`, 직접 식별정보까지
연결된 경우만 자동 S로 전제를 수정했다.

IR이 텍스트의 canonical source이므로 P2는 우선 IR을 판정한다. 다만 렌더링 뒤
PDF에서 근거가 보존됐는지 별도 결정론적 검사를 추가해 최종 모델 입력과
생성 검증 입력 사이의 차이를 막는다.

## Approaches Considered

### Approach A: 프롬프트·taxonomy 보강

P1/P2 프롬프트와 제6호 taxonomy에 연결 조건과 O 예외를 추가한다.

- Effort: S
- Risk: High
- Pros: 가장 작은 변경이며 빠르게 재실행할 수 있다.
- Cons: LLM이 일반 설명문을 구체 근거라고 다시 해석해도 코드가 막지 못한다.
- Reuses: 기존 `Pass2Assessment`, taxonomy rendering, evidence quote validator.

### Approach B: 구조화된 S 판정 계약과 결정론적 게이트

원문 참고 S 경로에 관계 중심 P2 계약을 추가하고, 목표 불일치 재생성,
`hard_case` 검수 상태, PDF 근거 보존 검사를 연결한다.

- Effort: M
- Risk: Low
- Pros: 현재 오통과 원인을 계약 수준에서 차단하고 결과 상태가 명확하다.
- Cons: 기존 C/S/O 범용 P2와 audit bridge의 호환 경계를 신중히 나눠야 한다.
- Reuses: ordered block IR, blind P2 호출, evidence quote validator, typed failures,
  HTML pipeline report, 기존 renderer.

### Approach C: 완전한 O/S 대응쌍 생성기

원문 하나에서 최소 차이의 O/S 두 문서를 동시에 생성하고 delta manifest와
source-group split을 강제한다.

- Effort: L
- Risk: Medium
- Pros: 가장 강한 반사실 학습 데이터와 누수 방지 구조를 제공한다.
- Cons: 현재 10건 검증 범위를 넘어 생성·분할·audit 전반을 확장한다.
- Reuses: source snapshot/hash, generation provenance, group-aware holdout 기반.

## Recommended Approach

Approach B를 채택한다. 프롬프트만 고치는 A는 현재와 같은 의미적 오통과를
다시 허용하고, C는 첫 수정으로는 범위가 크다.

### 계약

원문 참고 S 경로에서 사용하는 새 내부 계약은 다음 의미를 가진다.

```text
SensitiveAssessment
  verdict: S | O | hard_case
  assertions: SensitiveAssertion[]
  rationale: string

SensitiveAssertion
  subject_role
  subject_span
  attribute_kind
  value_span
  link_span
  identification_strength: direct | indirect | masked
```

- `S`는 하나 이상의 assertion, `direct` 식별, 비마스킹 구체값 또는 직접
  식별자와 연결된 개인 사정을 요구한다.
- `O`는 승인 가능한 assertion을 가질 수 없다. P2가 검토한 후보와 거부 이유는
  별도 진단 필드로 보존할 수 있다.
- `hard_case`는 `indirect` 또는 `masked` assertion을 하나 이상 요구한다.
- 모든 span은 실제 block ID와 해당 block에 유일하게 존재하는 quote를 사용한다.
- 주체와 값은 같은 문장·key-value 항목·표 행에 있거나, `link_span`이 둘의
  관계를 명시해야 한다.

### 정책 모듈

S/O 정책을 프롬프트 문자열에만 두지 않고 versioned policy로 중앙화한다.

- 외부인 역할과 직원 역할
- 직접 식별정보와 고위험 개인 속성
- 직원 업무 공개정보 O 목록
- 직원 인사평가·징계 O 예외
- 집계 O 규칙
- 마스킹·간접 식별 hard-case 규칙

P1 prompt guidance와 P2 guidance는 같은 policy renderer를 사용한다. 정책
version과 hash는 prompt bundle 및 실행 기록에 포함한다.

### 실행 상태와 재생성

학습 데이터 승인 상태를 기술 실행 성공과 분리한다.

```text
accepted_s
hard_case_review
regenerating_after_o
excluded_after_retry
pipeline_failed
```

초기 P1→P2 결과가 O면 동일 원문·목표로 P1부터 한 번 다시 실행한다. 두 번째도
O면 `excluded_after_retry`로 끝낸다. `hard_case`는 재생성으로 명확한 S로
세탁하지 않고 원문 경계 사례로서 사람 검수 큐에 보낸다.

### PDF 보존 게이트

`accepted_s` 후보를 렌더링한 뒤 PDF에서 텍스트와 표 셀을 추출한다. assertion의
subject/value/link quote를 정규화해 PDF 추출 결과에서 다시 찾는다.

- 모두 보존: 최종 `accepted_s`
- 일부 누락: `pipeline_failed` 또는 `render_evidence_missing`
- PDF 추출 자체 실패: 명시적 typed failure

이 단계는 PDF에서 새 의미 판정을 하지 않는다. IR에서 승인된 근거가 렌더링
과정에서 손실되지 않았는지만 확인한다.

### HTML 보고서

각 문서에 다음을 모두 보여준다.

1. 원문
2. 원문 S/O 적합성
3. P1 생성 IR과 생성 본문
4. P2 S/O/hard-case 판정
5. 구조화된 assertion과 정확한 근거
6. 재생성 시 1차·2차 시도 비교
7. 렌더링 PDF 근거 보존 결과
8. 기술 실행 상태와 학습 데이터 승인 상태

`succeeded=true`만으로 화면에 “성공”을 표시하지 않는다.

## Open Questions

- 운영 규모에서 재생성을 한 번보다 더 허용할지는 10건 파일럿의 실패율과
  비용을 본 뒤 결정한다.
- O/S 대응쌍의 자동 생성은 Approach B가 안정된 뒤 별도 확장한다.
- PDF 텍스트 추출기가 표의 행 관계를 얼마나 보존하는지는 실제 10건으로
  확인하고, 필요하면 좌표 기반 검사를 후속 작업으로 둔다.

## Success Criteria

### 결정론적 테스트

다음 최소 골든 사례를 고정한다.

1. 개인정보 항목 설명만 있는 문서 → O
2. 외부인 이름만 있는 문서 → O
3. 외부인 이름 + 실제 형식 전화번호 → S
4. 외부인 이름 + 건강·복지 사정 → S
5. 직원 이름·부서·업무 연락처 → O
6. 직원 주민등록번호 → S
7. 직원 인사평가·징계 → O
8. 개인 식별 없는 집계정보 → O
9. 마스킹된 이름·연락처 → hard_case
10. 신청번호 + 개인 사정 → hard_case
11. 신청번호 + 직접 식별정보 + 개인 사정 → S
12. 동일 표 행의 외부인과 개인정보 → S

변형 테스트는 S 사례에서 값 또는 연결근거를 제거하면 O/hard-case로,
직원 업무 연락처를 개인 연락처로 바꾸면 O에서 S로 전이하는지 확인한다.

### 10건 live 파일럿

- 항목명·정책 설명만으로 승인된 S는 0건이다.
- 모든 `accepted_s`에는 검증된 관계 assertion이 최소 1개 있다.
- 모든 `accepted_s`의 근거가 최종 PDF에서도 보존된다.
- O 불일치, 재생성, 제외, hard-case가 HTML에 별도 상태로 보인다.
- 원문 기반 산출물의 파일명이 원문 파일명과 일치한다.
- 각 문서의 원문→P1→P2→렌더링 과정이 HTML에서 눈으로 검토 가능하다.

## Distribution Plan

기존 batch CLI와 로컬 HTML/PDF 산출 경로를 사용한다. 새 패키지나 서비스는
배포하지 않는다. 기존 pytest와 opt-in live batch가 CI 및 수동 검증 진입점이다.

## Next Steps

1. S/O policy와 `SensitiveAssertion`/`SensitiveAssessment` 계약을 추가한다.
2. source-referenced S 경로의 P1/P2 prompt와 응답 모델을 새 계약에 연결한다.
3. O 판정 시 한 번 재생성하고 승인 상태를 분리한다.
4. taxonomy의 직원 인사평가·징계 S 포함 규칙을 이번 연구 정책에 맞게 수정한다.
5. PDF 근거 보존 게이트와 HTML 단계 표시를 추가한다.
6. 골든·변형 테스트를 실행한다.
7. 원문 10건을 다시 생성해 HTML 보고서를 검수한다.

## The Assignment

10건 파일럿에서 `accepted_s`와 `hard_case_review`를 사람이 전수 확인하고,
각 문서에 대해 “누구의 어떤 정보가 어디에서 연결되는가”를 한 줄로 기록한다.
코드의 자동 판정과 사람 판정이 다른 사례는 다음 regression fixture로 고정한다.

## What I noticed about how you think

- `지원자의 전화번호 및 이메일주소`라는 문장을 보고 곧바로 “값이 아니라
